# relic-yokoyama-review

変更が解決する問題と、そのために増える複雑さ・運用負担・影響範囲を比較する。動くことだけでなく、設計、既存利用者、導入後の保守まで一続きに確認する。

## 調査の進め方

変更の目的、仕様、設計資料、比較対象を確認する。差分から呼び出し元、データの生成・保存・利用、既存実装、テスト、導入手順まで追い、次を明らかにする。

- 直そうとしている問題は何か。誰が、どの条件で困るのか。
- 変更は問題の中心を直しているか。影響範囲や管理対象を必要以上に増やしていないか。
- 実装、型、DB、API、画面、設計資料、テストが同じ契約を表しているか。
- 既存データ、旧実装、導入順序、失敗途中の状態を含めて成立するか。

類似実装があれば比較し、差に理由があるか確認する。静的確認で判断できないものは、最小限の再現や実行結果で確かめる。

## 判断する観点

| 観点 | 確認すること |
|---|---|
| 目的と変更量 | 問題の深刻度に対して変更量・影響範囲・管理対象が大きすぎないか。利用者や運用者が得る効果を説明できるか。問題のない環境まで変更に巻き込んでいないか。キャッシュや独自基盤など、失効・同期・障害対応を伴う仕組みは最後の手段として扱う。 |
| 仕様・設計との一致 | 実装、設計資料、UIの用語、API、ファイル構造、処理順が一致するか。違う場合は、どちらを正とするか決めて一緒に更新する。同じ概念に類義語を混ぜず、名前から対象・主体・操作を判別できるようにする。コードだけでは失われる重要な経緯や制約は、維持される場所へ残す。 |
| 既存データと導入 | デフォルト値や権限を追加するとき、保存済みデータにも必要な状態が作られるか。マイグレーションは可能なら手作業を避け、適用中の不整合時間と失敗余地を小さくする。適用済みのマイグレーションを書き換えず、現行アプリのモデルやコールバックに依存しない。新旧コードが混在する時間、サービス間のデプロイ順、ロールバックも確認する。 |
| 失敗時の契約 | 起こり得る業務上の失敗と、想定外のシステム障害を分ける。想定外の保存・更新・削除失敗を成功扱いにせず、例外または失敗結果として呼び出し元へ返す。複数更新は途中失敗時の状態を確認し、必要なら同じ境界で原子的に扱う。例外を広く握りつぶさず、扱えるものだけ処理する。 |
| データと型の保証 | 所有者・権限・関連先を入力から保存まで追う。一意性、外部キー、NULL可否など永続的な条件は、適切ならDBでも保証する。型で保証した値へ場当たり的な実行時分岐を重ねず、入力境界で不正値を処理する。実装上の0/1や内部表現を利用側へ漏らさず、公開契約の型に合わせる。 |
| 責務と共通化 | 業務処理を入口や表示層へ散らさず、変更理由と知識を持つモデル・ユースケース・フォーム等へ置く。一方、利用箇所が少ない処理や固有の手続きを、将来予測だけで共通層へ移さない。共通化は影響範囲と改修難度を増やすため、概念と契約が安定してから行う。同じ判定を複数層へ重ねてダブルメンテにしない。 |
| 複雑さと保守 | 分岐、引数、状態、ファイルの責務を減らせないか。未完成・未使用のコード、依存、設定、生成物を残さない。今回不要な整理を混ぜず、独立した変更は分ける。大きな共通ファイルや暗黙に広く公開される仕組みでは、名前と配置から適用範囲を限定する。 |
| テスト | 変更した振る舞い、失敗、権限、境界値、既存データを、責務を持つ層で保証する。仕様変更で既存テストの期待が変わるなら、実装と同じ理由でテストも更新する。テスト間でコールバックや設定を変更して副作用を残さない。テスト用の値は実世界で別の意味を持つ値を避け、静的レビューで保証できない操作は手動確認も検討する。 |
| 性能・運用・安全性 | 推測だけで最適化せず、実データ量、クエリ、インスタンス生成、メモリ、初回応答、再試行負荷を確認する。大量処理では分割単位と失敗後の再開を考える。管理画面の操作でも、同じ資源を使う利用者側への影響を確認する。認証情報、公開範囲、CI権限、外部送信は最小権限・最小公開にする。ログや通知は、誰がどう対応するかまで決まっている場合に追加する。 |

## 指摘を確定する

候補ごとに反証する。

1. 今回の変更で導入・悪化した問題か。既存問題なら、この変更の成立に必要な理由があるか。
2. 上位層、共通処理、DB、型、運用手順がすでに保証していないか。
3. 実際の要件・データ量・信頼境界に対して必要か。管理者しか触らない経路など、リスクを受容できる条件はないか。
4. 提案によって管理対象、共通層、導入手順、別環境への影響が増えないか。より小さい修正で目的を満たせないか。
5. 指摘の修正案が問題を解消し、別の契約を壊さないか。未検証のコード例は、その旨を明示する。

同じ原因の指摘はまとめる。直す価値はあるが今回の必須条件でないものと、仕様確認が必要なものを、不具合から分ける。

## 出力

日本語で結論を先に書く。各指摘には対象ファイル・行、発生条件、結果、根拠、必要なら最小の修正方針を添える。

- `[MUST]`: マージ前に解消すべき不具合、契約違反、重大な保守・運用上の問題。
- `[COULD]`: 効果はあるが、今回の目的達成に必須ではない改善。
- `[Q]`: 仕様や運用判断がなければ確定できない確認事項。

確認済みの範囲、実行した検証、重要な未確認事項を短く示す。資料にない要件や優先度を補わず、指摘数を増やすための提案はしない。
