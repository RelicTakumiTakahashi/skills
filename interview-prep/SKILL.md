# 一次面接

候補者の書類から、一次面接60分の資料を作る。最終合否は判断しない。面接官がよい判断をするための材料と視点を渡す。

候補者は書類選考を通過している。技術力の確認は面接の目的にしない。

## 1. 前提

### 私たちについて

- 人月ビジネス(時間を売る)から「価値を売る」チームへの転換の真っ只中にいる。
- AIで既存業務を爆速化し、浮いた工数で顧客の事業をイノベーションする。「早く終わらせること」をプロの技術と呼び、稼働時間の長さを成果と見なさない。
- AI効率化による高単価化、AIを用いた新規提案、自社サービスの3本柱で事業を進めている。
- 募集するのは「エンジニアリング・ビジネスマン」。コードが書けるだけの人でも、提案がうまいだけの人でもない。顧客のビジネス課題を技術で解き、それを「売れる形」にできる人。
- 主な業務:顧客のビジネス課題のヒアリングとAIを組み込んだ提案、仕様書がない状態からの要件定義とプロジェクト推進、要望を実装可能なタスクへ落とし込むこと、契約構造(請負・準委任・バリューベース)まで踏み込んだ提案、内製化支援・伴走、実装(実装は目的ではなく手段)、ナレッジ共有と育成(教える時間は業務そのもの)。
- AIコーディングツールは全員が日常的に使う。事業とどう向き合うかを最も重く見る。

私たちについて書いてよいのは、この前提とユーザーが述べた事実だけ。働き方や体制を推測で補わない(例:「PMが顧客と開発の間に立つ」「数字で示す仕事が多い」などを勝手に書かない)。

### 求める人

- 顧客のビジネス課題をヒアリングし、解決策を「売れる形」で提案できる
- 仕様書がない状態から、曖昧な要望を構造化して要件に落とし込み、プロジェクトを前に進められる
- 技術を目的ではなく、ビジネス価値を最大化する手段と捉えている
- AI活用を「使ったことがある」で終わらせず、工数削減・提案・新しいアウトプットにつなげている
- 一人の成果より、チームごと前に進めることに面白さを感じる。新しいやり方に不安や温度差があるメンバーにも、挑戦するメリットを説いて巻き込める。メンバーを育てられる
- 「なんでこれ人月なんですか?」と、慣習に素朴な疑問をぶつけられる。技術トレンドや役割の変化を自分から取りに行ける

あれば望ましい経験:PoCから運用まで持っていった新規事業・自社サービスの経験、役職に関係なく人を動かした実例、顧客と開発チームの間に立った実例、自分が抜けても回る仕組みづくり、内製化支援などの伴走、失敗とその学びを自分の言葉で語れること。これらは「あれば望ましい経験」であり、私たちの役割の説明として候補者に伝えない。

向いていない人:仕様書をもらってから動きたい人、稼働時間の長さで評価されたい人、一人で完結する仕事がしたい人。

明確なNGタイプ(兆候があれば必ず指摘する):
- 顧客への提案は得意だが、開発チームへの配慮が足りず現場を疲弊させる人(書類上の兆候例:成果がすべて一人称で、「チームで」「メンバーが」という主語が出てこない)
- 自分一人でやればいいと考え、育成や組織の変化に関心がない人。単独のスーパープレーヤーは求めていない(書類上の兆候例:育成・採用・仕組み化・ドキュメント整備への言及がない)
- 技術的な正しさへの固執が強く、ビジネス上の妥当性とのバランスを欠く人
- マネジメント経験はあるが、自分の手で提案・要件定義をしていない人

## 2. 書類の読み方

- 次は評価にも質問にも使わず、資料でも触れない:年齢、性別、国籍、出身地、家族構成、婚姻状況、信条・宗教、健康状態・既往歴、居住地(通勤可否の確認を超えるもの)、写真の印象、出身校のランク(学位・専攻は評価してよい)、経済状況。空白期間や短期在籍はマイナス扱いしない(理由が不明なら確認に回すだけ)。
- 書類に書かれていないことを推測で補って評価しない。書類だけでは判断できない点は、そう書いて面接での確認に回す。
- 推薦状の褒め言葉、社名や事業規模の印象を根拠にしない。大企業での成果は分業の中で出たものが多いので、本人が担った範囲を分けて聞く。
- 数値成果は、実測・見込み・目標を区別する。
- 主語のない成果や、メンバーが主語の文がない書類は、本人の判断とチームの成果を分けて確認する。
- 自己PRの自己申告(「〜を提案した」など)は、誰にどう通したかまで聞いて事実に落とす。提案内容は語れても通し方を語れなければ、構想止まりの可能性がある。
- 書類に答えが書いてあることは聞かない。判断が表れる部分(条件の決め方、何を後回しにしたか、どう測ったか)を聞く。

## 3. 質問の選び方

メイン5問と追加1問で作る。メインの合計は35分。次の軸を基本とし、書類に応じて入れ替えてよい。

1. 事業課題に自ら向き合った経験:依頼を待たずに課題を見つけ、要件に落とし込み、成果につなげたか。技術的に面白いからやったのか、事業価値から逆算したのか。課題に気づいてから提案が採用されるまでの流れ
2. 育成とチームリード:品質・期限を守りながら育て、任せる範囲を広げたか。新しいやり方に不安や温度差があるメンバーをどう動かしたか。「相手の状態→自分の働きかけ→相手の変化」を時系列で語れるか。巻き取った経験を正直に認め、反省を言語化できるのも良い回答
3. 判断の根拠と成果の検証:本人が決めた部分と、効果の測り方。納品・リリース後に顧客の事業がどう変わったかを追っているか(数字がなくても、追おうとした行動があればよい)
4. AI活用:自分の仕事の進め方がAIでどう変わったか(作業時間の変化を数字で、AIが弱いと感じる部分の認識も)。AIを使って自分で作り切ったか。「AIを組み込んだ受託」と「頼まれる前に自分からAIで攻める提案」は別物として見る
5. 社外への提案と今回の役割への期待:課題の聞き出し方、提案と契約の形、納品後の関わり
- 追加:うまくいかなかった経験と学び。または、転職の経緯と理由(一貫した軸があり、私たちを選ぶ理由とつながるか。環境や他者への不満だけで語られていないか)

- 例は書類の具体的なエピソードから選ぶ。直近の経験を優先し、別の例は留意点に予備として書く。
- 書類で十分に読める実績の再確認は最小限にする。
- 「求める人」とNGタイプの各項目が、どの質問か深掘りで確かめられるかを照合する。漏れは質問を増やさず深掘り項目に足す。
- AI活用の質問は技術力の試験ではない。仕事のやり方が変わったかを見る。

## 4. 各質問の書式

```
## Qn <見出し>

**質問前に伝えること**:「<話題を示す一言>」

**質問**　「<メインの1問>」

**聞き取れなければ深掘り**

- <ラベル>:<確かめること>
- (3〜4項目)

**見極めたいこと**:
**良い回答**:
**危険信号**:
**留意点**:
**回答メモ**:
```

- メインの質問は1問だけ。背景・対応・結果に分けて順番に聞かない。答えに含まれなかった点だけを深掘りで聞く。
- 候補者がそのまま聞いて意図がわかる話し言葉にする。社内用語や評価用の言葉を使わない。
- 「質問前に伝えること」は話題を示すだけでよい。私たちに触れるときは前提の事実だけを書く。
- 太字のラベルは、コロンを太字の外に出す(`**見極めたいこと**:`)。内側に入れると太字が崩れることがある。

## 5. 資料全体の構成

1. タイトル「<姓>様 一次面接 <面接日 YYYY-MM-DD>」(例:「李様 一次面接 2026-11-16」)。面接日がわからなければユーザーに確認する。作成日は書かない
2. 面接の目的:目的を1文(最終合否はこの資料では判断しない)、私たちの前提、書類から読める強み、確かめるべき差、書類時点で未確認の点(各項目に対応するQ番号)、NGタイプごとの兆候の有無(兆候なし/気になる記述あり/書類では判断できない)
3. 進行 60分:表(挨拶・自己紹介・志望理由 5分/Q1〜Q5 計35分/候補者からの質問・対話 20分)。表の下に「各質問はメインの1問だけを聞き、答えに含まれなかった点を深掘りで確認する。追加質問は時間に余裕がある場合に使う」「良い回答・危険信号は目安とし、言い回しだけで判断しない」
4. 志望理由:(記入欄)
5. Q1〜Q5
6. 時間があれば聞く追加質問
7. 候補者からの質問と対話(質問と回答/持ち帰り事項)
8. 面接後の整理:各軸の行動事実の記入欄、書類時点の懸念を打ち消した事実、残った懸念と追加確認事項、追加質問を聞いた場合の欄、判断前の確認(第一印象や話の巧さ、社名・事業規模の印象に引っ張られていないか、本人とチームを区別できているか、未確認・未経験・問題行動を混同していないか、属性情報を判断に混ぜていないか)

「その他の補足確認」の節は作らない。

## 6. 出力

- 資料はClaude Docsのドキュメントとして作る。Docsが使えない場合は、Markdownで返す。
- 返答は結論から、平易な日本語で簡潔に書く。断定できない点は「〜と読める」「〜の可能性がある」と書き、書類だけでは判断できないと書くことを恐れない。
