# 開発メンバー向けの周知文

対象ブランチを取り込んだ開発メンバーが、自分の環境を更新して作業を再開できるようにする。エンドユーザー向けのリリース案内や本番デプロイの手順は対象外。

## 1. 誰にどんな作業が必要か調べる

指定された PR、または会話で直前に扱った PR を調べる。指定がなければリモートの既定ブランチと直近のマージを確認する。候補が複数あれば対象を聞く。PR の取り込み先は、その PR のベースブランチから特定する。

変更ファイルと関連する差分を読み、変更前の環境で作業していたメンバーに何が残るかを確認する。GitHub なら `gh pr view` でファイル、ベースブランチ、マージコミットを取得できる。ロックファイルは、必要なパッケージとバージョンに絞って確認する。

| 変更箇所 | 確かめること |
|---|---|
| 依存の定義、ロックファイル、ランタイムのバージョン指定 | 開発環境での版の切り替え、依存の再インストール |
| 環境変数の見本、設定取得ツール | 追加する項目名と取得方法。秘密値は周知文に含めない |
| マイグレーション | 開発用 DB に差分を適用する手順 |
| Dockerfile、Compose、Dev Container | 対象サービスと、ビルド・再作成・再起動のどれが必要か |
| セットアップスクリプト、タスク定義 | 新しく必要なツール、更新された初期化手順 |

実行コマンドは対象リポジトリの開発手順・タスク定義・スクリプトから調べる。一括タスクがある場合も、変更されたサービスが実行対象に含まれるか確かめる。取り込み時に必要な処理が自動で済むなど、読み手の作業がなければ「手元で必要な作業はなく、周知は不要です」と伝えて終える。

## 2. 配布する手順を検証する

- 検証用のチェックアウトに変更が入っているか確認する。マージ済みなら `git merge-base --is-ancestor <マージコミット> HEAD` が使える。利用中のブランチを切り替える必要がある場合は先に確認する。
- 読み手と同じ作業ディレクトリ・実行環境で、掲載するコマンドを順番どおりに実行する。サービス停止、データの消去、長時間の環境変更を伴う操作は、影響と対象を示して実行前に確認する。
- 終了コードと出力、実行後のバージョンや適用状態を確かめる。すでに更新済みの環境で「適用対象なし」と出た場合、旧状態から更新できるかは未確認として扱う。検証のために利用中のデータを巻き戻さない。
- 共通して起きる対話やエラーは、その場で確認した応答や解決方法を控える。個人の環境だけで起きた問題は除く。
- 必須の手順を一つでも確認できなければ、投稿用の周知文は出さず、確認済みの手順、未確認の手順、検証に必要な環境や操作を伝える。過去の記録だけで検証済みとしない。任意の補足だけが未確認なら、その補足を外せる。

## 3. Slack に貼れる形で渡す

冒頭に何が変わったかを一文で書き、どのブランチを取り込んだ後の作業かを伝える。各手順は「依存を入れ直す」のように動詞で始め、実行するコマンドをコードブロックに入れる。最後に、完了を確認するコマンドと期待する結果を添える。

以下は書式の見本。山かっこは対象リポジトリで確認した内容に置き換える。

````
<変更内容>。
<対象ブランチ> を取り込んだら、リポジトリのルートで次の順に実行してください。

1. <必要な作業>
```
<検証したコマンド>
```

2. <更新結果を確認する>（<期待する結果> が表示されれば完了）
```
<確認コマンド>
```
````

- 読み手がそのままコピーできるよう、プロンプト記号やプレースホルダーを残さない。作業ディレクトリの移動が必要なら手順に含める。
- 検証した手順を一本に絞る。実際に対話が出た場合は、入力する文字と、その入力で何が起きるかを該当するコマンドの直後に書く。
- 本文はです・ます体にし、番号、改行、コードブロックで構成する。PR の経緯や別環境での確認依頼、宛先のメンションは含めない。
- 周知文全体をバッククォート四つで囲む。ブロックの外で、検証した内容と、未確認のために外した補足や別途共有すべき話題があれば短く伝える。
- Slack への下書き保存や投稿は、明示的に依頼された場合だけ行う。
