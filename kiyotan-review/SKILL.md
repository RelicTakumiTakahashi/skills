# kiyotan-review

修正する価値のある問題を、根拠とともに伝える。各観点は現行仕様に照らして判断する。

## 調査の進め方

比較対象、仕様、プロジェクトの指示を確認し、変更が守るべき条件を正常系・失敗時・既存利用者について整理する。差分から呼び出し元、依存先、共通処理、保存先、結果の利用先、テストまで追う。

以下から変更に関係する観点を選び、条件を破る入力や実行順序を探す。問題を見つけた後も、変更に関係する他の境界を確認する。

レビュー依頼では調査と指摘を行う。修正・投稿・承認・マージは依頼された範囲で行う。

## 振る舞いを確認する観点

| 変更に含まれる境界 | 確認すること |
|---|---|
| 入力・権限・情報露出 | 識別子の存在だけでなく、取得・作成・関連付けの所有範囲を検証する。通常経路を通らない入力や、サーバーが決定すべき状態の上書きを確認する。クエリ・パス・URL・コマンド・表示への入力と検証位置、ログ・例外・返却値・一時保存からの情報露出を追う。 |
| 更新・失敗・再実行 | 部分成功後に何が残るか、例外を処理して成功扱いにならないか。内部状態の巻き戻しと外部の副作用を区別し、中断・再試行時の未処理、重複、復旧方法を確認する。非同期の受付と完了を混同しない。 |
| 同時実行・順序 | チェックと更新の間に別処理が入っても、一意性・残量・順序を保てるか。ロックの対象・範囲・複数プロセスでの有効性、重複イベント、遅い応答、取消後の完了を追う。 |
| 値・時刻・データ取得 | 欠損・空・ゼロ、空の結果と失敗、全件と一部を区別する。正規化後の制約、上限下限と等号、単位・丸め・精度・タイムゾーン・期限の基準を確認する。ページ境界の欠落・重複と順序、キャッシュや一時ファイルの所有者・条件・版による識別、更新・削除・権限変更時の失効も見る。 |
| 既存データ・互換性・導入 | 保存済みの値と移行手順、適用済み環境での意味を確認する。API・イベント・保存形式の型、省略値、エラー、副作用を利用側と照合し、新旧混在、移行失敗、設定欠落時も追う。状態や時刻を別の業務上の意味で代用していないか。共有部品の利用先、無関係な変更・デバッグ処理、依存更新の実際の解決版と利用APIも確認する。 |
| 資源・負荷・終了処理 | データ量に対する問い合わせ回数、全件保持、並列数、時間制限、再試行の負荷と他処理への影響を確認する。ファイル・接続・ロック・購読が成功・例外・取消時に解放されるか。 |
| 操作・結果の伝達 | 呼び出し側・利用者・運用者へ成功、失敗、進捗、次の行動が伝わるか。再操作や遅い応答で古い成功・誤った対象を示さないか。重大操作の確認・復旧手段、UI変更ではキーボード操作・フォーカス・状態の伝達を見る。 |

## 設計とテストを判断する

動作が正しくても、読む負担や同じ知識を変更する負担が具体的に増えるなら提案できる。「望ましい方向」と「今回直す必要性」を分け、実害・契約・規約・変更負担と修正範囲で判断する。資料にない期限や改修コストは推測しない。

| 場面 | 提案の根拠と、見送れる条件 |
|---|---|
| 責務・分離 | 入出力調整、設定、業務判断、計算、表示の混在や、特定機能の都合が共通処理へ入り込む点を見る。同じ判断・定義の重複は変更時の食い違いで評価し、知識の所在や変更理由で分離する。単純な処理を切り出して読む場所が増えるだけなら不要。既存の分離も短さだけで統合させない。 |
| 名前・引数 | 対象・操作・返り値・副作用・完了時点が読めるか。情報の重複した受け渡しや大きな構造への不要な依存を確認するが、取得コストや特定時点の値を保持する意図は保つ。改名は誤認や読解負担を根拠にし、実害がなく広く波及するなら見送れる。 |
| 拡張 | 具体的な追加用途があり、判断の分散やデータ移行を招く場合は境界を見直す。未確定の用途や構想だけで汎用化を必須にしない。 |
| テスト | 戻り値・呼出しの有無だけでなく、変更した状態・副作用を保証しているか。必要に応じて失敗、初回、再実行、空、境界、権限外を検証する。委譲側は委譲の契約、担当側は振る舞いを保証し、全階層へ同じ詳細を要求しない。テスト名・前提・期待を揃え、assertion数だけで分割しない。既存の準備を活用し、不要な外部依存を増やさず、必要な最小限のテストを実行する。 |

## 指摘を確定する

候補を出した後と最終出力の直前に、次の反証を探す。

1. **今回の変更か。** 変更前と比較する。既存の問題は、今回の変更を成立させるために対応が必要な理由がなければ必須修正に含めない。
2. **別の場所で保証されていないか。** 上位・共通処理の権限、整合性、例外処理、テストを確認する。差分にないことを不足の証拠にしない。
3. **仕様や意図に反しないか。** 履歴の保持や契約通りの空結果などを誤って問題にしない。提案した修正が実際に問題を解消しない反例も探す。
4. **具体的な根拠があるか。** 不具合は「変更箇所 → 発生条件・実行順序 → 破られる条件 → 影響」で示す。設計提案は具体的な読解・変更負担、最小限の改善方向、今回は許容できるかを示す。「長い」「怖い」「遅そう」や特定の実装方式の好みだけで要求しない。

同じ原因の指摘はまとめ、根拠不足は確認事項に留める。修正する価値のある指摘に絞る。

## 出力

日本語で結論から簡潔に書き、各指摘にレビュー対象時点のファイル・行と上記の根拠、必要なら修正方針を添える。指定の出力形式があれば従う。

- 確認できた不具合は明確に述べ、実害に応じた優先度を付ける。
- 改善提案は`[WANT]`／`[IMO]`、仕様依存の未確認事項は`[Q]`に分ける。
- 確認範囲、重要な未確認事項、実行した検証を短く示す。読んでいない領域を確認済みにせず、全観点のチェックリストは毎回出さない。実装評価とCI・承認・マージ条件を区別する。
